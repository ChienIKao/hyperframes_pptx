# 智慧城市資料平台規劃

## 背景與動機

現況盤點與痛點

### 現況問題

- 各局處資料格式不一，整合成本高
- 缺乏即時儀表板，決策依賴**月報**
  - 月報平均延遲 3 週
  - 人工彙整易出錯
- 市民查詢管道分散

<!-- 這頁強調痛點，約 1 分鐘。提到去年的颱風應變案例。 -->

### 使用者需求

根據 2026 年 Q2 訪談 42 位承辦人員的結果整理：

1. 一站式查詢
2. 自動化報表
3. 行動裝置可用

### 系統架構

![架構示意圖](assets/chart.png)

### 技術選型

| 層級 | 技術 | 理由 |
|---|---|:---:|
| 前端 | Vue 3 | 團隊熟悉 |
| 後端 | Go | 高效能 |
| 資料庫 | PostgreSQL + PostGIS | 空間查詢 |
| 快取 | Redis | 低延遲 |

### 部署腳本範例

```bash
docker compose -f prod.yml up -d
kubectl apply -f k8s/
```

### 導入時程

- 第一階段：資料盤點與標準制定，預計耗時兩個月，需要各局處配合提供資料字典
- 第二階段：平台建置，包含資料管線、儀表板、權限管理
- 第三階段：試營運與教育訓練
- 第四階段：正式上線
- 第五階段：持續維運與擴充，每季檢討指標
- 第六階段：開放資料 API 對外服務
- 第七階段：跨縣市資料交換
- 第八階段：AI 預測模型導入
- 第九階段：成效評估與下一期規劃，撰寫結案報告並辦理成果發表會

## 預期效益

> 讓資料成為城市治理的共同語言

### 量化指標

- 報表產製時間：**3 週 → 即時**
- 資料整合成本降低 `40%`
- 市民滿意度提升至 85%
